1. Introducción: en qué consiste el proyecto y cómo funciona

El proyecto es una pareja de aplicaciones .NET (misma arquitectura que MiReplica) para la empresa SERFAGAB, que fabrica tableros eléctricos y necesita administrar sus materiales (pernos, planchas, pintura, etc.) clasificados por tipo de material.

2. Requisitos previos: SQL Server, SSMS, .NET 7 y Visual Studio

  • SQL Server corriendo en la máquina (el proyecto usa server=., instancia local).
  • SQL Server Management Studio (SSMS) para ejecutar el script DB_SERFAGAB_DSWI_completo.sql y revisar la base.
  • .NET 7 SDK/Runtime. En esta PC hay SDK 10 con runtime .NET 7, y la plantilla se creó con -f net7.0.
  • Visual Studio 2026 (o 2022+) con la carga de trabajo "ASP.NET y desarrollo web".
La cadena de conexión es un requisito de la BD: la API lee de appsettings.json esta cadena: server=.;database=DB_SERFAGAB_DSWI;user=sa;password=sql;TrustServerCertificate=True; En este proyecto se usa autenticación de SQL Server con el usuario sa y contraseña sql (a diferencia de MiReplica, que usaba Integrated Security=True). Comprobación rápida de la BD: desde SSMS verifico que exista DB_SERFAGAB_DSWI con las tablas tbl_tipo_material, tbl_material, tbl_proveedor, tbl_orden_compra, tbl_detalle_orden_compra y los SPs, antes de levantar la API.

4.5. Services (ADO.NET + SPs) y el manejo de NULL en Descripcion

Aquí está toda la lógica de base de datos, con el mismo patrón de MiReplica: List temporal + while (reader.Read()) para lecturas, y bool resp + ExecuteNonQuery() > 0 + transacción para escrituras.

TipoMaterialService.list() (solo lectura)

Services/TipoMaterialService.cs 
using Microsoft.Data.SqlClient;
using ProyectoGrupalDSWI_Serfagab.Interfaces;
using ProyectoGrupalDSWI_Serfagab.Models;

namespace ProyectoGrupalDSWI_Serfagab.Services
{
    public class TipoMaterialService : ITipoMaterialService
    {
        private readonly string? conexion;

        public TipoMaterialService(IConfiguration configuration)
        {
            conexion = configuration.GetConnectionString("conexion");
        }

        public List<TipoMaterial> list()
        {
            List<TipoMaterial> temporal = new List<TipoMaterial>();

            using (SqlConnection con = new SqlConnection(conexion))
            {
                using (SqlCommand command = new SqlCommand("sp_list_tipo_material", con))
                {
                    command.CommandType = System.Data.CommandType.StoredProcedure;
                    con.Open();
                    using (SqlDataReader reader = command.ExecuteReader())
                    {
                        while (reader.Read())
                        {
                            TipoMaterial tipo = new TipoMaterial
                            {
                                IdTipoMaterial = reader.GetInt32(0),
                                Nombre = reader.GetString(1),
                                Descripcion = reader.IsDBNull(2) ? "" : reader.GetString(2),
                            };
                            temporal.Add(tipo);
                        }
                    }
                }
            }
            return temporal;
        }
    }
}
¡La línea clave de este Service!

Descripcion = reader.IsDBNull(2) ? "" : reader.GetString(2),

La columna descripcion de tbl_tipo_material es NULLABLE. reader.GetString(2) lanza una excepción (InvalidCastException) si la celda contiene NULL en vez de texto. Por eso primero preguntamos con reader.IsDBNull(2): si es NULL, usamos "" (cadena vacía); si no, leemos el texto.

MaterialService: los 5 métodos

using ProyectoGrupalDSWI_Serfagab.Models;

namespace ProyectoGrupalDSWI_Serfagab.Services

        public MaterialService(IConfiguration configuration)
        {

        public List<Material> list()

            using (SqlConnection con = new SqlConnection(conexion))

            {

                {
                    command.CommandType = System.Data.CommandType.StoredProcedure;
                    command.Parameters.AddWithValue("@idMaterial", IdMaterial);
                    con.Open();
                    using (SqlDataReader reader = command.ExecuteReader())
                    {
                        while (reader.Read())
                        {
                            material = new Material
                            {
                                IdMaterial = reader.GetInt32(0),
                                IdTipoMaterial = reader.GetInt32(1),

                                UnidadMedida = reader.GetString(3),

                            };
                        }
                    }
                }
            }
            return material;
        }

        // insert/update/delete: bool resp = false + ExecuteNonQuery() > 0 + transacción
        public bool insert(Material material)
        {
            bool resp = false;

            using (SqlConnection con = new SqlConnection(conexion))
            {
                con.Open();
                SqlTransaction tran = con.BeginTransaction();
                try
                {
                    using (SqlCommand command = new SqlCommand("sp_insert_material", con))
                    {
                        command.Transaction = tran;
                        command.CommandType = System.Data.CommandType.StoredProcedure;
                        command.Parameters.AddWithValue("@idTipoMaterial", material.IdTipoMaterial);
                        command.Parameters.AddWithValue("@nombre", material.Nombre);
                        command.Parameters.AddWithValue("@unidadMedida", material.UnidadMedida);
                        command.Parameters.AddWithValue("@stockActual", material.StockActual);
                        command.Parameters.AddWithValue("@precioReferencial", material.PrecioReferencial);
                        command.Parameters.AddWithValue("@descripcion", (object?)material.Descripcion ?? DBNull.Value);
                        resp = command.ExecuteNonQuery() > 0;
                        tran.Commit();
                    }
                }
                catch (Exception)
                {
                    tran.Rollback();
                }
            }
            return resp;
        }

Resumen de los 3 patrones de Service (igual que MiReplica):
  • list() → ExecuteReader + List temporal llenada en while (reader.Read()).
  • getById() → ExecuteReader, inicializa material = null: si el SP no devuelve filas, queda null y el controller responde 404. Obligatorio pasar @idMaterial.
  • insert/update/delete → bool resp = false, ExecuteNonQuery() > 0, todo dentro de una transacción (BeginTransaction + Commit/Rollback).
Sección especial: el manejo de NULL en "descripcion"

En este proyecto la columna descripcion es NULLABLE (en tbl_tipo_material y tbl_material). Eso obliga a dos cuidados que en MiReplica no existían (ahí todas las columnas eran NOT NULL):

1) En la LECTURA: reader.IsDBNull(...)

Descripcion = reader.IsDBNull(6) ? "" : reader.GetString(6),

reader.GetString(6) lanza InvalidCastException si la celda trae NULL (una celda NULL no es un string). IsDBNull(6) es una comprobación rápida de SqlDataReader: si es NULL, ponemos una cadena vacía ""; si no, leemos el texto con GetString. Así el modelo nunca recibe DBNull.

2) En la ESCRITURA: (object?)x ?? DBNull.Value

command.Parameters.AddWithValue("@descripcion", (object?)material.Descripcion ?? DBNull.Value);

AddWithValue no acepta null de C#: SQL Server necesita DBNull.Value para guardar un NULL real. Si el usuario dejó la descripción vacía, material.Descripcion será null, y con ?? DBNull.Value se envía DBNull.Value (NULL en la BD). El cast (object?) evita la ambigüedad del operador ?? con string.

Contraste con MiReplica y alternativa más simple

En MiReplica todas las columnas eran NOT NULL, por eso se usaba GetString y AddWithValue directos sin comprobaciones. En SERFAGAB, la alternativa para "calcar" ese estilo más simple sería declarar la columna como descripcion NVARCHAR(255) NOT NULL DEFAULT '' en el script SQL; entonces el código podría ser reader.GetString(6) y AddWithValue("@descripcion", material.Descripcion). Decidimos mantener la columna NULLABLE (más fiel al serfagab.sql de referencia) y por eso el manejo defensivo.

Errores que evita este manejo:
  1. Si descripcion es NULL en la BD y hago GetString directo → la API responde 500 con InvalidCastException.
  2. Si el JSON del POST/PUT no incluye "descripcion", la propiedad queda null y el AddWithValue directo lanza ArgumentNullException → 500. Con ?? DBNull.Value se inserta NULL sin error.

        {

            return Ok(await Task.Run(() => materiales));
        }

        [HttpGet("{IdMaterial}")]
        public async Task<IActionResult> GetById(int IdMaterial)
        {
            var material = _service.getById(IdMaterial);
            if (material == null)
            {
                return NotFound(new ApiResponse<object>
                {
                    message = "No se encontró el material con el id " + IdMaterial,
                    success = false,
                    data = ""
                });
            }
            else
            {
                return Ok(new ApiResponse<Material>
                {
                    message = "Material encontrado!",
                    success = true,
                    data = material
                });
            }
        }

        [HttpPost]
        public async Task<IActionResult> Post([FromBody] Material material)
        {
            var resp = _service.insert(material);
            if (resp)
            {
                return Ok(new ApiResponse<Material>
                {
                    message = "Material insertado correctamente!",
                    success = true,
                    data = material
                });
            }
            else
            {
                return BadRequest(new ApiResponse<object>
                {
                    message = "No se pudo insertar el material",
                    success = false,
                    data = ""
                });
            }
        }

        [HttpPut]
        public async Task<IActionResult> Put([FromBody] Material material)
        {
            var exists = _service.getById(material.IdMaterial);
            if (exists == null)
            {
                return NotFound(new ApiResponse<object>
                {
                    message = "No se encontró el material con el id " + material.IdMaterial,
                    success = false,
                    data = ""
                });
            }

            var resp = _service.update(material);
            if (resp)
            {
                return Ok(new ApiResponse<Material>
                {
                    message = "Material actualizado correctamente!",
                    success = true,
                    data = material
                });
            }
            else
            {
                return BadRequest(new ApiResponse<object>
                {
                    message = "No se pudo actualizar el material",
                    success = false,
                    data = ""
                });
            }
        }

        [HttpDelete("{IdMaterial}")]
        public async Task<IActionResult> Delete(int IdMaterial)
        {
            var exists = _service.getById(IdMaterial);
            if (exists == null)
            {
                return NotFound(new ApiResponse<object>
                {
                    message = "No se encontró el material con el id " + IdMaterial,
                    success = false,
                    data = ""
                });
            }

            var resp = _service.delete(IdMaterial);
            if (resp)
            {
                return Ok(new ApiResponse<object>
                {
                    message = "Material eliminado correctamente!",
                    success = true,
                    data = ""
                });
            }
            else
            {
                return BadRequest(new ApiResponse<object>
                {
                    message = "No se pudo eliminar el material",
                    success = false,
                    data = ""
                });
            }
        }
    }

            var content = await response.Content.ReadAsStringAsync();
            var lista = JsonConvert.DeserializeObject<List<Material>>(content) ?? new List<Material>();
            return await Task.Run(() => lista);
        }

        Task<Material> getMaterial(int IdMaterial)
        {
            var response = await _httpClient.GetAsync("api/Material/" + IdMaterial);
            var content = await response.Content.ReadAsStringAsync();
            var apiResponse = JsonConvert.DeserializeObject<ApiResponse<Material>>(content) ?? new ApiResponse<Material>();
            var material = apiResponse.data;
            return await Task.Run(() => material);
        }

        Task<List<TipoMaterial>> listTipos()
        {
            var response = await _httpClient.GetAsync("api/TipoMaterial");
            var content = await response.Content.ReadAsStringAsync();
            var lista = JsonConvert.DeserializeObject<List<TipoMaterial>>(content) ?? new List<TipoMaterial>();
            return await Task.Run(() => lista);
        }

        Task<string> insertar(Material material)
        {
            var json = JsonConvert.SerializeObject(material);
            var body = new StringContent(json, Encoding.UTF8, "application/json");
            var request = await _httpClient.PostAsync("api/Material", body);
            var response = await request.Content.ReadAsStringAsync();
            var apiResponse = JsonConvert.DeserializeObject<ApiResponse<object>>(response) ?? new ApiResponse<object>();
            var message = apiResponse.message;
            return await Task.Run(() => message);
        }

        Task<string> actualizar(Material material)
        {
            var json = JsonConvert.SerializeObject(material);
            var body = new StringContent(json, Encoding.UTF8, "application/json");
            var request = await _httpClient.PutAsync("api/Material", body);
            var response = await request.Content.ReadAsStringAsync();
            var apiResponse = JsonConvert.DeserializeObject<ApiResponse<object>>(response) ?? new ApiResponse<object>();
            var message = apiResponse.message;
            return await Task.Run(() => message);
        }

        Task<string> eliminar(int IdMaterial)
        {
            var request = await _httpClient.DeleteAsync("api/Material/" + IdMaterial);
            var response = await request.Content.ReadAsStringAsync();
            var apiResponse = JsonConvert.DeserializeObject<ApiResponse<object>>(response) ?? new ApiResponse<object>();
            var message = apiResponse.message;
            return await Task.Run(() => message);
        }

            var lista = await listMateriales();

9. Manejo de excepciones en los Services (mejora implementada)

Al revisar el proyecto con enfoque de profesor se detectó un problema de robustez en todos los Services de la API: los métodos de escritura (insert/update/delete) usaban este patrón:

Antes (en los 4 Services) 
catch (Exception)
{
    tran.Rollback();
}
¿Qué problemas tenía ese patrón?
  1. Se tragaba el error: el catch no capturaba la excepción en una variable ni la registraba. Si el SP fallaba (FK inválida, tipo de dato, conexión), nadie sabía por qué.
  2. El Rollback podía enmascarar el error original: si la conexión se rompió o la transacción ya se cerró, el propio tran.Rollback() lanza otra excepción que se escapa sin manejo y llega al cliente como un 500 sin detalles.
  3. El usuario no recibe información útil: el controller solo respondía "No se pudo insertar el material", imposible distinguir un problema de FK de un problema de conexión.

Solución implementada (nivel 2): inyectar ILogger<T> en cada Service y usar un catch que loguee la excepción original y haga el Rollback seguro (si el Rollback también falla, se captura y se loguea por separado, sin perder el error original).

9.1. Constructor: inyectar ILogger<T>

Services/MaterialService.cs (constructor) 
private readonly string? conexion;
private readonly ILogger<MaterialService> _logger;

public MaterialService(IConfiguration configuration, ILogger<MaterialService> logger)
{
    conexion = configuration.GetConnectionString("conexion");
    _logger = logger;
}

El mismo cambio se aplicó a ProveedorService, TipoMaterialService y OrdenCompraService. ASP.NET Core resuelve ILogger<T> automáticamente por inyección de dependencias; no hay que registrarlo en Program.cs.

9.2. El nuevo patrón de catch (ejemplo: MaterialService.insert)

Después (patrón en todos los métodos de escritura) 
catch (Exception ex)
{
    _logger.LogError(ex, "Error al insertar material {Nombre}", material.Nombre);
    try { tran.Rollback(); }
    catch (Exception rbEx) { _logger.LogError(rbEx, "Fallo adicional al hacer rollback en insert de material"); }
}
Cómo funciona:
  • ex es el error original: se registra con _logger.LogError(ex, "..."), que escribe el mensaje y el stack trace en la consola / ventana Output.
  • El Rollback se ejecuta dentro de un try propio: si falla, la excepción se captura como rbEx y se loguea por separado. Así ninguna excepción queda sin capturar y no se pierde el error original.
  • El {Nombre} entre llaves es un placeholder estructurado: el framework lo reemplaza por el valor y lo guarda como campo buscable en los logs.

9.3. Más detalles de la implementación

  • 4 Services modificados: MaterialService (insert/update/delete), ProveedorService (insert/update/delete), TipoMaterialService (insert/update/delete) y OrdenCompraService (solo insert, que escribe cabecera + detalles).
  • Transacciones de una sola sentencia: se mantuvieron tal cual (decisión del equipo para conservar el estilo de la pareja MiReplica). Nota académica: en operaciones de un solo ExecuteNonQuery la transacción no aporta nada (la sentencia ya es atómica); solo es necesaria donde hay múltiples sentencias, como OrdenCompraService.insert().
  • Mensajes al usuario: se conservó la respuesta genérica (BadRequest "No se pudo..."), pero ahora el detalle real queda en el log del servidor. El siguiente nivel (nivel 3) sería propagar el error al controller para devolver mensajes específicos (ej. FK inválida) o un middleware global de ProblemDetails.

10. Consistencia de la API: listas envueltas en ApiResponse<T> (mejora implementada)

Al revisar la API con enfoque de profesor se detectó una inconsistencia en el contrato: todos los endpoints envolvian sus respuestas en el sobre ApiResponse<T> (message, success, data), pero los endpoints de lista (GET sin id) devolvian el array crudo.

¿Cuál era el problema?
  • El mismo recurso se servía con dos formatos distintos: GET /api/Material devolvía [ { ... }, { ... } ] mientras GET /api/Material/1 devolvía { "message": "...", "success": true, "data": { ... } }.
  • El cliente tenía que recordar la forma de cada endpoint: listMateriales() deserializaba List<Material> directo, pero getMaterial() deserializaba ApiResponse<Material>. Acoplamiento frágil.
  • Si el service de la lista fallaba, no había sobre para devolver un error uniforme (success: false + message).
  • En Swagger el contrato se veía inconsistente: mismo recurso, dos formas de respuesta.

Solución implementada: envolver las listas en el sobre ApiResponse<List<T>> y actualizar el cliente para que lea data. El contrato queda uniforme en toda la API (igual que MiReplica).

10.1. API: antes y después (aplicado en los 4 controllers)

Antes (Controllers/MaterialController.cs, Get) 
[HttpGet]
public IActionResult Get()
{
    var materiales = _service.list();
    return Ok(materiales);
}
Después (mismo método) 
[HttpGet]
public IActionResult Get()
{
    var materiales = _service.list();
    return Ok(new ApiResponse<List<Material>>
    {
        message = "Lista de materiales!",
        success = true,
        data = materiales
    });
}
Los 4 controllers modificados: MaterialController ("Lista de materiales!"), TipoMaterialController ("Lista de tipos de material!"), ProveedorController ("Lista de proveedores!") y OrdenCompraController ("Lista de ordenes de compra!"). Todos con ApiResponse<List<T>>.

10.2. Cliente MVC: leer la lista desde data

El cliente tenía 7 consumos de lista que deserializaban el array crudo: MaterialController (listMateriales, listTipos), TipoMaterialController (listTipos), ProveedorController (listProveedores) y OrdenCompraController (listOrdenes, listProveedores, listMateriales). Todos se cambiaron a este patrón:

Después (patrón en los 7 consumos de lista) 
var apiResponse = JsonConvert.DeserializeObject<ApiResponse<List<Material>>>(content)
    ?? new ApiResponse<List<Material>>();
return apiResponse.data ?? new List<Material>();
¡API y cliente se cambian juntos! Si solo se cambia la API y no el cliente, el cliente se rompe: ya no encuentra un array, sino un objeto con data. Por eso la corrección es coordinada en ambos proyectos.

10.3. Cómo probar el cambio

  1. Compilar ambos proyectos (dotnet build): verifica que API y cliente compilen con 0 errores.
  2. En Swagger, GET /api/Material (y Proveedor, TipoMaterial, OrdenCompra): ahora responde { "message": "Lista de materiales!", "success": true, "data": [ ... ] }.
  3. En el cliente MVC: http://localhost:5217/Material, /TipoMaterial, /Proveedor y /OrdenCompra deben seguir listando normal, y los dropdowns (tipos en Create/Edit de Material, proveedores y materiales en OrdenCompra) siguen cargando.
